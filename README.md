# HelpDesk Ticket Management System

A full stack helpdesk application for submitting, assigning, tracking, and reviewing support tickets. The project uses an Angular 21 single page application, a Go REST API, and MySQL/MariaDB.

## Technology stack

- **Frontend:** Angular 21, TypeScript, RxJS, Angular Router, standalone components.
- **Backend:** Go 1.27+, `net/http` REST handlers, MySQL driver, JWT authentication, bcrypt password hashing.
- **Database:** MySQL or MariaDB using the MySQL wire protocol. PostgreSQL is not currently supported.
- **Local database setup used by this repository:** XAMPP MariaDB, normally at `127.0.0.1:3306`.

## Requirements to run locally

Install these tools on the computer that will run the project:

1. **Go 1.27 or newer** (the backend `go.mod` declares Go 1.27.2).
2. **Node.js and npm** compatible with Angular 21. The repository uses npm 11.10.0.
3. **MySQL or MariaDB**. XAMPP is one supported local option; start its MySQL service before starting the API.
4. Git, if cloning the project.

The frontend and backend are separate processes and should be run in separate terminals. The database must be running before the backend starts.

## First-time setup

### 1. Get the source

Clone the Git repository or unzip the complete project. Open a terminal in the project root (the directory containing `helpdesk-backend` and `helpdesk-frontend`).

### 2. Create the database and tables

Start MySQL/MariaDB. In a SQL console such as phpMyAdmin, run these repository scripts in order:

1. `helpdesk-backend/schema.sql` — creates `helpdesk_db` and the `users` table.
2. `helpdesk-backend/ticket_schema.sql` — creates the categories, tickets and comments tables and seeds standard categories.

These scripts use MySQL/MariaDB syntax (`AUTO_INCREMENT`, `ENUM`, `INSERT IGNORE`) and are intended to be safe to rerun where tables already exist. If using another database, provide an equivalent schema and change the backend implementation; PostgreSQL compatibility is not included.

### 3. Configure the backend

Create a private `.env` file by copying `helpdesk-backend/.env.example` to `helpdesk-backend/.env`. Set the values to match the local database account. Example for a fresh XAMPP install with root and no password:

```dotenv
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_USER=root
MYSQL_PASSWORD=
MYSQL_DATABASE=helpdesk_db
JWT_SECRET=replace-this-with-a-random-secret-at-least-32-characters-long
CORS_ORIGINS=http://localhost:4200,http://127.0.0.1:4300,http://localhost:4300
PORT=8080
```

Generate a unique, random JWT secret of at least 32 characters for each environment. Do not commit `.env` or a real secret. The backend `.gitignore` excludes `.env`.

### 4. Create user accounts

The API has no public registration route. Create an administrator manually with a bcrypt hash:

```powershell
cd helpdesk-backend
go run ./cmd/hash-password
```

Enter the password when prompted; it is hidden. Copy the generated hash into a SQL insert in phpMyAdmin, replacing the sample name, email and hash:

```sql
USE helpdesk_db;
INSERT INTO users (full_name, email, `password`, role)
VALUES ('Helpdesk Administrator', 'admin@example.com', '<paste-generated-bcrypt-hash>', 'ADMIN');
```

Create at least one support account so tickets can be assigned and critical tickets can be created. The helper uses the configured `.env`, prompts for a hidden password, and creates or updates the local account `support@helpdesk.local` with role `SUPPORT`:

```powershell
go run ./cmd/ensure-support-user
```

For ordinary end users, insert a row into `users` with role `USER` and a bcrypt hash generated by `go run ./cmd/hash-password`. Never put a plaintext password in the database.

### 5. Install frontend packages

```powershell
cd ..\helpdesk-frontend
npm install
```

If `package-lock.json` is present, `npm ci` is also suitable for a reproducible clean install.

## Start the application

### Terminal 1: start the Go API

From the project root:

```powershell
cd helpdesk-backend
go run .
```

The API loads `.env`, checks that `JWT_SECRET` is at least 32 characters, and verifies the database connection at startup. On success it listens at `http://localhost:8080`. Keep this terminal open.

### Terminal 2: start Angular

From the project root:

```powershell
cd helpdesk-frontend
npm start
```

Open [http://localhost:4200](http://localhost:4200). If port 4200 is already in use, choose another port and ensure its browser origin is listed in `CORS_ORIGINS`, for example:

```powershell
npm start -- --port 4300
```

Then open `http://localhost:4300`. The Angular app calls the API at `http://localhost:8080` (configured in `src/app/auth.service.ts`).

## How the application works

1. A user signs in through the Angular login page. The Go API validates the bcrypt password and returns a JWT bearer token.
2. Angular stores the token in session storage, or local storage when “remember me” is selected, and sends it on protected API calls.
3. Role-based route guards and API checks separate `USER`, `SUPPORT`, and `ADMIN` capabilities.
4. Users create tickets and view their own tickets. Support staff see tickets assigned to them and can comment or update their assigned work. Administrators can view all tickets, assign support staff, change priority, and review workflow decisions.
5. Ticket, comment and account data is stored in MySQL/MariaDB. The dashboard statistics are computed from the fetched ticket list.

## Implemented features against the task brief

| Task requirement | Implementation |
| --- | --- |
| User, Ticket, Category, Comment entities | MySQL tables in `schema.sql` and `ticket_schema.sql`; user roles are `USER`, `SUPPORT`, `ADMIN`. |
| Ticket fields and audit times | Tickets store ID, unique ticket number, title, description, category ID, priority, status, assignee, creator, created/updated times, plus a resolution description. |
| Priority values | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` are validated and stored as a database enum. |
| Status values | Requested statuses are supported, with additional approval/confirmation statuses described below. |
| Create tickets | `POST /api/tickets`; validates fields/category and returns the created ticket. Critical tickets are assigned to an available support user at creation; creation fails if no support user exists. |
| Assign tickets | Admin-only `PATCH /api/tickets/{ticketNumber}/assignment`; assignee must have SUPPORT role. Critical tickets cannot be left unassigned. |
| Update tickets | Admins can update workflow state and assignment; admins can update priority separately. Closed tickets are blocked from edits. |
| Add comments | `GET` and `POST /api/tickets/{ticketNumber}/comments`; comments include author and creation time. Closed tickets cannot receive new comments. |
| Change status | `PATCH /api/tickets/{ticketNumber}/status`; support staff can change status only on tickets assigned to them; admins can manage workflow. |
| Ticket details | `GET /api/tickets/{ticketNumber}` with role-scoped access. |
| Search and filters | `GET /api/tickets` accepts search, status and priority query parameters. |
| Pagination | API accepts optional `page` and `limit` and returns pagination metadata. Angular list screens also paginate the returned list in the browser (8 per page). |
| Closed ticket business rule | Closed tickets cannot be edited or commented on. |
| Resolution description | Required when an administrator marks a ticket resolved. Support staff must add a work comment before requesting resolution; their resolution is subject to admin review. |
| Critical ticket assignment | Critical ticket creation auto-assigns the first available support user; changing a ticket to critical requires a support assignee. |
| Assigned support status updates | API checks the signed-in support user is the assignee before allowing status changes. |
| Dashboard | Shows Total Tickets, Open Tickets, In Progress, Resolved and Critical Tickets, with additional priority/status breakdowns and recent tickets. |
| Angular ticket UI | Includes dashboard, all/admin tickets, my tickets, assigned tickets, create form, ticket detail, assignment, comments, status/priority controls, filters and pagination. |

### Additional workflow statuses

The application adds three internal states to implement review and confirmation steps:

- `PENDING_APPROVAL` — support requested ticket closure; an administrator must review it.
- `PENDING_RESOLUTION_APPROVAL` — a support resolution is waiting for administrator review.
- `PENDING_USER_CONFIRMATION` — after approval, the ticket creator confirms the outcome; confirmation closes the ticket.

These statuses supplement `OPEN`, `ASSIGNED`, `IN_PROGRESS`, `RESOLVED`, and `CLOSED`. As a result, a support user's “resolve” or “close” action may first create a pending state rather than immediately setting the final status.

## REST API overview

All endpoints are served by the Go API at `http://localhost:8080`. Protected routes require `Authorization: Bearer <access_token>`.

| Method | Route | Purpose |
| --- | --- | --- |
| `POST` | `/api/auth/login` | Authenticate and obtain a JWT. |
| `GET` | `/api/auth/me` | Get the current authenticated user. |
| `POST` | `/api/auth/logout` | Revoke the token for the current API process. |
| `GET` | `/api/categories` | List ticket categories. |
| `GET` | `/api/tickets` | List tickets visible to the role; supports search, priority/status filters and optional pagination. |
| `POST` | `/api/tickets` | Create a ticket. |
| `GET` | `/api/tickets/{ticketNumber}` | Read one ticket. |
| `PATCH` | `/api/tickets/{ticketNumber}` | Save admin workflow/assignment changes. |
| `PATCH` | `/api/tickets/{ticketNumber}/assignment` | Assign or unassign a ticket (admin). |
| `PATCH` | `/api/tickets/{ticketNumber}/priority` | Change priority (admin). |
| `PATCH` | `/api/tickets/{ticketNumber}/status` | Change status under role and workflow rules. |
| `GET` / `POST` | `/api/tickets/{ticketNumber}/comments` | List or add a comment. |
| `PATCH` | `/api/tickets/{ticketNumber}/closure` | Admin review of a closure request. |
| `PATCH` | `/api/tickets/{ticketNumber}/resolution-review` | Admin review of a resolution. |
| `PATCH` | `/api/tickets/{ticketNumber}/resolution-confirmation` | Ticket creator confirms a resolution and closes the ticket. |
| `GET` | `/api/support-users` | List support users (admin). |

Pagination can be requested as `/api/tickets?page=1&limit=20`; the response includes `page`, `limit`, `total` and `total_pages` along with `tickets`. Without pagination parameters the API returns the complete role-scoped list, which the current Angular client then filters/pages locally.

## Troubleshooting

- **`JWT_SECRET must contain at least 32 characters`:** replace the sample value in `helpdesk-backend/.env` with a longer random secret.
- **Database connection failure:** start MySQL/MariaDB, verify host/port/user/password/database in `.env`, and confirm both SQL scripts have been run.
- **Unknown database/table:** create the database with `schema.sql`, then create the application tables with `ticket_schema.sql`.
- **Login fails:** verify that the account exists in `users`, its role is correct, and the stored password is a bcrypt hash. There is no registration endpoint.
- **Critical ticket cannot be created/assigned:** create at least one user with role `SUPPORT` and make sure the selected assignee is a support account.
- **Frontend reports it cannot reach the API:** keep the Go API running at port 8080; check browser CORS origin against `CORS_ORIGINS`.
- **Angular reports the port is occupied:** start with `npm start -- --port 4300` (or another free port) and add that exact origin to `CORS_ORIGINS` before starting the backend.

## Current scope notes

- This repository currently targets MySQL/MariaDB only; the task's PostgreSQL option is not implemented.
- Ticket creation is available to all three roles, although the normal workflow is for end users to create tickets.
- The API supports server-side pagination, while the current Angular screens request the full role-visible list and paginate it client-side.
- Logout token revocation is held in memory and is cleared if the API process restarts; signed tokens still expire. Login sessions expire after 12 hours by default or 30 days when “remember me” is selected.
- User registration and account administration screens are not included; accounts are provisioned through SQL and the support-user helper.
